# 2026.256.1128 — fix(ci): quote the build workflow step name that broke its YAML

## Summary

The bootstrap `build.yml` step name

```yaml
- name: Fetch the welded plugin pins (single source: opencharly/charly)
```

has an unquoted `: `, so YAML reads it as a nested mapping. GitHub rejected the workflow and
refused a dispatch. This quotes the scalar so the file parses and dispatches. One line, no
behavior change.

## How tested

### Before — the file on `main` does not parse

```
$ git show origin/main:.github/workflows/build.yml > /tmp/build-broken.yml
$ node yamlcheck.js /tmp/build-broken.yml
/tmp/build-broken.yml: PARSE ERROR: Nested mappings are not allowed in compact mappings at line 51, column 15:
exit=1
```

GitHub agreed — the push run reports a workflow-file issue, and a dispatch is refused:

```
$ gh run view 34754246448 -R opencharly/charly-lib
X This run likely failed because of a workflow file issue.

$ gh workflow run build.yml -R opencharly/charly-lib
could not create workflow dispatch event: HTTP 422: Workflow does not have 'workflow_dispatch' trigger \
  (https://api.github.com/repos/opencharly/charly-lib/actions/workflows/357056882/dispatches)
```

### After — the fixed file parses (full output)

```
$ node yamlcheck.js .github/workflows/build.yml
.github/workflows/build.yml: PARSE OK; triggers={"workflow_dispatch":{"inputs":{"charly_ref":{"description":"charly ref holding scripts/host-command-plugins.txt (the pins)","required":true,"default":"main"},"sdk_ref":{"description":"opencharly/sdk ref carrying cmd/charly-lib-gen","required":true,"default":"main"},"sdk_version":{"description":"github.com/opencharly/sdk Go module version the host requires","required":true,"default":"v0.2026254.523"},"version":{"description":"release CalVer to tag+publish (empty = build-only)","required":false,"default":""}}}}; jobs=build
exit=0
```

The same full parse was run on all three workflow files after the change
(`pr-validator.yml`, `tag-on-merge.yml` parse `OK`).

## RCA (R1) — how an unparseable workflow reached `main`, and recurrence

This repo was **bootstrapped from empty**: there was no `main` (and therefore no org
`charly/pr-validator` on it) when the first tree was created, so no PR gate parsed the workflow
before it became the default branch. That is the missed control — a brand-new repo has no gate
until its dispatchers are on the default branch, and those dispatchers are themselves in the first
tree. Recurrence is now closed: the `charly/pr-validator` + `tag-on-merge` dispatchers are live on
`main` (confirmed in `gh workflow list`), so every subsequent change — including this one — is
PR-gated, and the build workflow's own dispatch is the end-to-end check.
